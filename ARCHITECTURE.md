# Architecture

## Pipeline Overview

```
source (&str)
  → [parser]              → ParsedDocument
                             Raw event stream: notes, rests, chords, directives,
                             lyrics syllables per measure. No note measure grouping yet.
  → [grouper]             → Score
                             Notes grouped into measures; lyrics paired to each
                             measure's lyric slots (tie-aware);
                             parts organized into MultiPartMeasure slices;
                             optional `# sequence` section resolved into
                             Score.sequence spans.
  → [compiler]            → CompileResult
                             Logical grid: each note/rest assigned to a column,
                             underlines computed, slur spans recorded.
  → [consolidator]        → CompileResult
                             Mixed notes/lyrics rows split; duplicate rows with
                             identical content suppressed per measure.
  → [grid_layout]         → Vec<GridPage>
                             Grid elements placed into rows with heights and column
                             counts; rows wrapped across pages; slur arcs resolved
                             to same-system or cross-system variants.
  → [coordinate_resolver] → Vec<AbsolutePage>
                             Every element assigned absolute x/y coordinates in
                             points; grid geometry collapsed to flat element list.
  → [renderer]            → Vec<SvgDocument>
                             SVG primitives (Text, Line, Circle, Path) produced
                             for each absolute element.
  → [serializer]          → Vec<String>
                             SVG strings, one per page, ready to write to disk.
```

## Layer Details

### Parser
- Module: `src/parser/`
- Entry: `parser::parse(source: &str, filename: &str) -> Result<ParsedDocument, IrrecoverableError>`
- Key types: `ParsedDocument` (also carries `sequence: Option<SequenceSection>` and `sequence_parse_errors: Vec<RecoverableError>` from the optional `# sequence` section — see **Sequence resolution** in the glossary; also carries `abbreviation_references: Vec<AbbreviationReference>` — every `[Abbrev]` key-prefix reference found in `# score`, in file order, each `{ abbreviation, span }` with `span` covering just the trimmed abbreviation text (excluding brackets/whitespace) — see **Rename-symbol support**), `ParsedTimedTrack`, `ParsedScore`, `ScoreEvent` (includes `PercussionHit(ParsedPercussionHit)`; `LabelChange(String)`'s `Spanned` wrapper carries a span narrowed to just the quoted label text, not the whole `label="..."` token), `ParsedNote` (carries `Accidental` for melody notes; tie intent via `tie_to_next_span: Option<Span>` with `tie_to_next()` accessor; also carries `tuplet: Option<TupletInfo>` — see **Tuplet** in the glossary), `ParsedRest` (carries `implicit_fill: bool` — true when this rest was synthesized by `desugar::implicit_fill` to stand in for a declaration absent from this measure group, rather than written by the composer as an explicit `0`; copied through `GroupedRest`/`ElementContent::Rest`/`GridContent::Rest`/`PostArcGridContent::Rest`/`AbsoluteContent::Rest` to `SvgVariant::OmittedPartRest`, which `render_omitted_part_rest` draws as a vector glyph — mirroring the conventional Western "whole rest": a thin horizontal cap line, wider than and sitting flush above, a short solid block — instead of `render_rest`'s ordinary `0` text — see **Omitted-part rest** in the glossary), `ParsedChordNote` (also carries `Accidental` and `tie_to_next_span`), `ParsedPercussionHit` (`ParsedNote` minus pitch/accidental — carries duration, dotted, group membership, tie/slur fields), `TupletInfo` (`{ num, den }` — see **Tuplet** in the glossary), `ParsedMetadata`, `JianPuPitch`, `Accidental` (`Sharp`/`Flat`/`Natural`; applies to both melody notes and chord notes), `Syllable`, `Soundfont` (vocal/piano/string; selects MIDI channel+program — on a `PartKind::Percussion` part, the number is instead a fixed GM percussion key rather than a GM program number, and is not validated against the melodic instrument catalog), `PartDecl` (carries `soundfont`, `volume`, `octave_offset`, `kind: PartKind`, `abbreviation_span: Span` — the abbreviation token's own byte span on its declaration line, used by rename-symbol — `PartKind::Percussion` reuses `&[ScoreLineRole::Notes]` for its score line roles), `SequenceSection` (parsed from `src/parser/sequence_parser.rs`'s `parse_sequence(content, offset) -> (Option<SequenceSection>, Vec<RecoverableError>)` — a comma-unzipped list of section-label references, each a `SequenceEntry { label, label_span, part_filter, span }` where `part_filter: Option<PartFilter>` comes from an optional `(...)` suffix; `PartFilter { kind, parts, part_spans }` with `kind: PartFilterKind` either `Omit` (a `(-abbrev -abbrev ...)` suffix naming part abbreviations to omit from that occurrence's playback, e.g. `Chorus(-S -A2)`) or `Only` (an `(abbrev abbrev ...)` suffix, no leading `-`, naming the only parts to keep for that occurrence — every other declared part is omitted — e.g. `Chorus(S A2)`); a suffix mixing `-abbrev` and `abbrev` tokens is a recoverable error, resolving to `part_filter: None`; `label_span`/`part_spans` are the byte spans of just the label text and each filtered abbreviation (used by rename-symbol) — see **Sequence resolution** in the glossary).

### Grouper
- Module: `src/grouper/`
- Entry: `grouper::group(doc: ParsedDocument) -> Result<Score, IrrecoverableError>`
- Key types: `Score` (carries `sequence: Option<Vec<SequenceSpan>>`, resolved by `resolve_sequence()` in `src/grouper/sequence_resolution.rs` — see **Sequence resolution** in the glossary), `SequenceSpan` (`label`, `start`, `end`, `omit_parts`, `part_filter_display`: an inclusive resolved measure-index range for one `# sequence` entry, plus `omit_parts: Vec<String>` — the concrete part abbreviations to omit from that occurrence's MIDI/WAV playback, always an omit-shaped list even when the entry wrote an `Only` filter (resolved to its complement against `# parts`) — and `part_filter_display: Option<PartFilterDisplay>` (`{ kind, parts }`, reusing `PartFilterKind`) carrying the suffix as written, for the "Sequence: ..." summary line, `None` when the entry has no suffix — see **Sequence resolution**), `MultiPartMeasure` (carries `bpm`/`key`/`time_signature`/`label` (all non-persisting on this type — see below) plus the always-resolved, persisting `merge_duplicate_measures_across_parts`/`hide_resting_parts` booleans), `PartRow` (Timed), `PartSlice` (carries `soundfont`, `volume`, `octave_offset`, `resolution_multiplier: u32`, copied unchanged from the source `GroupedMeasure::resolution_multiplier`; see **Tuplet** — and `beat_group_size: u32`, copied unchanged from the source `GroupedMeasure::beat_group_size`), `Notes`, `NoteEvent` (includes `Percussion(GroupedPercussionHit)`), `GroupedNote`, `GroupedRest` (carries `implicit_fill: bool`, copied unchanged from `ParsedRest::implicit_fill` — see **Omitted-part rest** in the glossary), `GroupedChordNote` (`GroupedNote`/`GroupedChordNote` use `tie_to_next_span` + `tie_to_next()` accessor; all four `Grouped*` note types also carry `tuplet: Option<TupletInfo>`, copied through unchanged from the corresponding `Parsed*` field — see **Tuplet** in the glossary), `GroupedMeasure` (intermediate: notes + `paired_lyrics: Vec<Vec<Syllable>>` — one entry per verse, tie-paired against the notes independently per verse — plus `resolution_multiplier: u32` — see **Tuplet** — and `beat_group_size: u32`, the quarter-beat width of one beam group under the time signature in effect for that measure: `4` for simple meters, `6` for compound meters (6/8, 9/8, 12/8, ...), computed by `PartGrouper::beat_group_size` from the time signature tracked via `TimeSignatureChange` events and unscaled by `resolution_multiplier`). `PartSlice.lyrics: Vec<Lyrics>` carries the same one-entry-per-verse shape through to the compiler; a part's verse count is per-measure (see **Lyrics line**/**Verse** in the glossary).
- `src/tuplet.rs`'s `resolution_multiplier_of(events: &[Spanned<ScoreEvent>]) -> u32` / `apply_resolution_multiplier(events: Vec<Spanned<ScoreEvent>>, resolution_multiplier: u32) -> Vec<Spanned<ScoreEvent>>` is a stage-agnostic pair used by both the parser and the grouper (see **Tuplet** in the glossary for the parser-side use). On the grouper side, `part_grouper_group::group_timed_track` calls both once per measure (one `ParsedMeasureSlot::Real`'s event list), before that measure's events reach `PartGrouper`: `resolution_multiplier_of` scans for `TupletInfo` tags and computes `resolution_multiplier = lcm(every tagged event's num)`, then `apply_resolution_multiplier` multiplies every event's `duration` by it (plain notes too, so the measure's grid stays proportionally consistent) and further multiplies tuplet-tagged events by `den / num` (exact, since `resolution_multiplier` is a multiple of `num`). `PartGrouper::begin_measure_slot(resolution_multiplier)` (called once per `ParsedMeasureSlot::Real`, before its rescaled events are pushed) scales the capacity check (`PartGrouper::effective_capacity() = capacity * resolution_multiplier`) so a measure's flush boundary still lands correctly post-rescale; the multiplier resets back to `1` only once that measure actually flushes (`flush_measure`), since the accumulating measure isn't always flushed by the time all its events have been pushed (e.g. the score's trailing measure, flushed later by `finish`). `resolution_multiplier` defaults to `1` and the rescale is then a no-op, so non-tuplet music is unaffected. `midi::midi_notes::duration_to_ticks(quarter_beats, multiplier)` divides `multiplier` back out when converting a (possibly rescaled) duration to MIDI ticks; grid-column pixel width needs no equivalent division — see **Tuplet**.
- `merge_duplicate_measures_across_parts`/`hide_resting_parts` on `MultiPartMeasure` are resolved (not `Option`) by `DirectiveGrouper` (`src/grouper/directive_grouper.rs`): seeded from `Metadata::merge_duplicate_measures_across_parts`/`Metadata::hide_resting_parts` (the `# metadata` default) and overridden from a given measure onward by a `merge_duplicate_measures_across_parts=`/`hide_resting_parts=` directive line, persisting like `bpm`/`key`/`time` until the next override — unlike those three, they carry the fully resolved value on every measure rather than `Some` only where changed, since downstream consumers (`compiler::compile_measure`, `consolidator::consolidate_block`) need a plain value per call and have no rendering reason to know whether it just changed.

### Compiler
- Module: `src/compiler/`
- Entry: `compiler::compile(score: &Score) -> CompileResult`
- Key types: `CompileResult` (carries `tuplet_spans: Vec<TupletSpan>` alongside `slur_spans`, populated the same way — see below), `MeasureBlock` (carries `represents_measures: usize`, the number of original source measures the block stands in for — `1` normally, `> 1` when a rest run was folded; consumers that walk blocks and assume one block == one measure must advance their measure counter by this field, not by `1`; also carries `merge_duplicate_measures_across_parts: bool`, copied from the originating measure's `MultiPartMeasure::merge_duplicate_measures_across_parts` — see Consolidator below; also carries `source_span: Span`, copied from the originating `MultiPartMeasure::source_span` (a merged rest-run block instead takes the min/max union of every measure's own span it stands in for, mirroring how `combiner` computes `MultiPartMeasure::source_span` itself) — this is what lets a layout-stage diagnostic like `WarningKind::MeasureOverflow` (see **Rod and spring** in the glossary) point at real source text even though grid layout runs after grouping/compiling), `MeasureRow` (carries `absorbed_rows: Vec<MeasureRow>`, empty until the consolidator merges another row's content into this one — see Consolidator below), `ColumnElement` (carries `note_id: Option<usize>` — see **Note identity** in the glossary), `ElementContent` (includes `PercussionHit`, threaded through `GridContent`/`PostArcGridContent`/`AbsoluteContent`/`SvgVariant::PercussionHit` and rendered centered via `render_percussion_hit`; also includes `MultiMeasureRest { count }`, threaded the same way through `GridContent`/`PostArcGridContent`/`AbsoluteContent`/`SvgVariant::MultiMeasureRest` and rendered via `render_multi_measure_rest` — see **Multi-measure rest** in the glossary; `Rest` also carries `implicit_fill: bool`, threaded the same way through `GridContent`/`PostArcGridContent`/`AbsoluteContent`/`SvgVariant::OmittedPartRest` and rendered via `render_omitted_part_rest` — see **Omitted-part rest** in the glossary), `SlurSpan`, `TupletSpan` (`{ part_index, measure_index, from_column, to_column, label }` — like `SlurSpan` but a single `measure_index` instead of `from_measure`/`to_measure`, since a tuplet never crosses a measure boundary; `label` is the tuplet's printed digit, e.g. `"3"` — see **Tuplet** in the glossary), `ArcKind`, `Decoration`
- `compiler::visible_part_indices(measure: &MultiPartMeasure) -> Vec<usize>` resolves which of `measure.parts` are actually compiled/sounded for that measure (an all-rest part is hidden when `hide_resting_parts` is in effect and at least one other part has real content). `compile_measure` uses it directly; `midi::timing::note_timings_seconds` (see **Note identity**) also walks `measure.parts` filtered through this same function, so its per-part `note_id` counters advance in lockstep with `ColumnElement::note_id`.
- `compile()`'s main loop still produces one block per source measure (preserving per-measure `cross_states`/`slur_spans`/bar-number bookkeeping); a post-pass `merge_rest_runs()` then folds maximal runs of 2+ eligible all-rest measures (see **Multi-measure rest**) into single blocks. Grid layout stays unaware of this folding — it only ever sees already-resolved blocks and lays out whatever `ElementContent`/`GridContent` variant it's given.
- `hide_resting_parts` (from `MultiPartMeasure::hide_resting_parts`, resolved per measure — see Grouper above) gates `compile_measure`'s omission of an all-rest part's row when at least one other part in the same measure has real content; when `false`, every part's row is rendered even if it's all rests.
- `PartSlice` also carries `resolution_multiplier: u32` (copied from the source `GroupedMeasure::resolution_multiplier` by `combiner::build_part_rows`; `1` for measures with no tuplets). `compiler::part_slice::compile_part_slice` reads it once per slice into `PartState::multiplier`, and every quarter-beat-grid literal in `part_slice.rs`/`part_slice_unit.rs` — the underline-count thresholds (base `1`/`2`/`3`), the note-dash spacing (base `4`) — is expressed as `BASE_CONST * multiplier` so a rescaled measure still lays out correctly. The beam-flush check itself (`beat_position % (beat_group_size * multiplier) == 0`) instead uses `PartState::beat_group_size`, read from `PartSlice::beat_group_size` — `4` for simple meters, `6` for compound meters — so a run of beamed notes/rests groups by dotted-quarter (3 eighth notes) rather than quarter-note in 6/8, 9/8, 12/8, etc. This is exact for untagged (non-tuplet) notes/rests in a rescaled measure, since their `duration` was scaled by exactly `multiplier` too; a tuplet-tagged unit's `duration` is additionally ratio-compressed (`* den / num` by `rescale_tuplets`), so before comparing against the underline-count thresholds, `compile_unit` first undoes that compression (`* num / den`, exact since `duration` was constructed as a multiple of `den`) to recover the note's written duration scaled by `multiplier` — so underline count reflects each note's written value (e.g. sixteenth notes get a double underline) independent of the tuplet's rescaled duration; the tuplet bracket/number is a separate overlay on top (see **Tuplet** in the glossary). `column: u32` itself needs no scaling — it's a pure additive grid index that already accumulates whatever (possibly rescaled) `duration` each unit was given.
- `TupletSpan`s are accumulated during the same pass as `SlurSpan`s, but by a separate, simpler mechanism (`compiler::tuplet_spans`'s `record_tuplet_tag`/`finish_tuplet_spans`, called from `compile_timed_unit`/`compile_unit` via the new `TimedUnit::tuplet()` trait method, and directly off `GroupedRest.tuplet` in `compile_rest`) since a tuplet never carries across measures: `PartState` holds one `current_tuplet: Option<PendingTupletSpan>`, reset fresh per `compile_part_slice` call, tracking the first/most-recent column of the contiguous run of notes/rests sharing one `TupletInfo` value; any break (an untagged event, or a different ratio) flushes it into `CompileResult.tuplet_spans`, remapped through `merge_rest_runs`'s `measure_to_block` exactly like `slur_spans`.
- A change in `merge_duplicate_measures_across_parts`/`hide_resting_parts` between two otherwise-collapsible measures forces a new run boundary in `merge_rest_runs()`, the same way a `label` does, since a merged block carries one resolved setting pair (taken from the run's first measure) for every measure it stands in for.

### Consolidator
- Module: `src/consolidator/`
- Entry: `consolidator::consolidate(result: CompileResult) -> CompileResult`
- Splits mixed `notes lyrics` rows into one notes row plus one lyrics row per verse (`ElementContent::Lyric { text, verse }` groups by `verse`), each verse's row getting a distinct `RowId` (`"{part}-lyrics-{verse}"`), then removes duplicate rows within each measure when their `elements` are identical (labels and ids are not compared). `slur_spans` are passed through unchanged.
- `merge_duplicate_measures_across_parts` (read per block from `MeasureBlock::merge_duplicate_measures_across_parts`, resolved per measure by the grouper — see Grouper above) gates only merges between rows with different `source_part_index`; rows from the same part still merge regardless.
- Because each verse gets its own `RowId`, a part's verse count changing between two measures simply changes which rows exist for that measure's block — `grid_layout::layout_systems::pack_into_systems`'s union-of-parts packing (see **System**) resolves this by padding the missing verse row(s) into the measure lacking them rather than breaking the system; no separate verse-count check is needed.
- When rows merge, the surviving row's own `label` is left untouched (it stays that row's own per-part identity, as compiled) — `consolidate_rows` only decides *which* rows to fold together, never what to call the result. That's deliberate: `consolidate_block` only ever sees one measure at a time, so it can't yet tell whether a content match holds for the whole system (in which case the merge should stick) or is a one-measure coincidence with a part that needs its own separate row elsewhere in the system (in which case it shouldn't). The *displayed* label is resolved later, by `grid_layout::layout_systems::resolve_label` (see Grid Layout below), once a system's full `RowId` membership is known.
- The merged-away row itself, in full — not just its `RowId` — (plus anything already in its own `absorbed_rows`, for a chain of three-or-more-way merges) is appended to the surviving row's `absorbed_rows` before it's discarded — otherwise that row's own real content (real `note_id`s, real click/playback targets) would vanish from the block with no trace, and a later measure in the same system whose parts *don't* merge would make `pack_into_systems`'s union-of-parts packing (see **System**) wrongly pad this block with a rest for a part whose notes are actually right here, merged into another row, or wrongly re-render it as a non-identity duplicate instead of its own genuine row. Each absorbed row's own `label` is likewise left untouched, so `resolve_label` can later read it as that part's true, unmerged identity.

### Grid Layout
- Module: `src/grid_layout/`
- Entry: `grid_layout::layout(result: &CompileResult, config: &RenderConfig, header: &Header, width_pt: f32, height_pt: f32, highlighted_measure_ranges: Option<Vec<MeasureRange>>) -> LayoutOutput` — `LayoutOutput { pages: Vec<GridPage>, diagnostics: Vec<Diagnostic> }`, where `diagnostics` currently only ever carries `WarningKind::MeasureOverflow` warnings (see **Rod and spring** in the glossary); both `document_render.rs` and `lib.rs`'s call sites merge these on top of `collect_measure_diagnostics`'s pre-layout, grouped-`Score` diagnostics before returning `RenderDocumentOutput`/`RenderOutput`. `highlighted_measure_ranges` is a list of disjoint, inclusive `global_measure_index` ranges (not a single range) so a `# sequence` chain selection spanning out-of-order entries can highlight several disjoint measures at once — see `grid_layout::highlight::compute_measure_highlights_for_range`.
- Key types: `GridPage` (carries `playback_cursor_targets: Vec<PlaybackCursorTarget>`, `part_label_click_targets: Vec<PartLabelClickTarget>`, `lyric_click_targets: Vec<LyricClickTarget>`, `lyric_label_click_targets: Vec<LyricLabelClickTarget>`, and `bar_number_click_targets: Vec<BarNumberClickTarget>` alongside `measure_highlights`/`error_highlights`/`measure_click_targets` — see **Playback cursor**, **Part label click target**, **Lyric click target**, **Lyric label click target**, **Bar number click target**), `GridRow`, `GridElement`, `GridContent` (includes `TupletBracket { label }` — same-system-only counterpart of `TieOrSlur`, with no `Tail`/`Head` split since a tuplet never crosses a system — resolved by `grid_layout::tuplet_placement::resolve_tuplet_spans` from `CompileResult.tuplet_spans`, mirroring `slur_placement::resolve_slur_spans`; see **Tuplet** in the glossary), `HAlign`, `VAlign`, `ColumnGeometry`, `MeasureColumnLayout`, `MeasureRange` (`start`/`end` — one inclusive `global_measure_index` range to highlight; `layout`'s `highlighted_measure_ranges` takes a `Vec` of these rather than one range so disjoint sequence-chain selections can each get their own highlight), `PlaybackCursorTarget` (`row_start`/`row_end`/`column_start`/`column_end` like `MeasureHighlight`, plus `source_part_index`/`note_id`, plus `click_row_end` — the note's own click/selection target's bottom row, which (unlike `row_end`) never absorbs a following lyric verse row; see **Note click target**), `PartLabelClickTarget` (`row_start`/`row_end`/`source_part_index`/`measure_index_start`/`measure_index_end` — see **Part label click target**), `LyricClickTarget` (`row`, `column_start`, `column_end`, `source_part_index`, `note_id`, `verse` — a single row/column-span pair, unlike `PlaybackCursorTarget`'s `row_start`/`row_end`, since one syllable never spans more than one row — see **Lyric click target**), `LyricLabelClickTarget` (`row`, `source_part_index`, `verse`, `measure_index_start`, `measure_index_end` — a single row within the fixed-width label region, the lyric-side mirror of `PartLabelClickTarget` — see **Lyric label click target**)
- `grid_layout::system_walk::for_each_system(page_systems, tuplet_bracket_map, header, base, hide_system_dividers, visit)` is the shared page→system→row-offset walk behind every `compute_all_*` function below (and `compute_all_measure_click_targets` above): it threads `row_offset` across system-divider rows, decoration rows, and each system's own musical row count, invoking `visit(page_idx, system, row_offset, tuplet_part_indices, musical_row_count)` once per non-empty system. Any state a caller accumulates across systems (a running `global_measure_index`, an output `Vec`) it owns itself and mutates from inside the closure.
- `grid_layout::playback_cursor::compute_all_playback_cursor_targets` (walks `for_each_system`) groups each `MeasureRow`'s elements by `note_id` per block and emits one `PlaybackCursorTarget` per contiguous run, scoped to that one part's own sub-rows (`note_row_spans`) rather than the whole system's row range `MeasureHighlight` uses. A tied note split across a system/line break, or a repeated measure position with no navigation-aware remapping, can legitimately produce more than one `PlaybackCursorTarget` sharing the same `(source_part_index, note_id)` — the frontend highlights all of them together. `playback_cursor::note_row_spans` (renamed from `part_row_ranges`) returns one `NoteRowSpan { row_start, playback_row_end, click_row_end }` per row template: `playback_row_end` absorbs any immediately-following lyric verse row(s) (feeding `PlaybackCursorTarget::row_end`), while `click_row_end` is captured before that absorption and never extends past the note row's own sub-rows (feeding `PlaybackCursorTarget::click_row_end`) — see **Note click target**.
- `grid_layout::click_targets::compute_all_part_label_click_targets` walks `for_each_system`, reusing `playback_cursor::note_row_spans`' `playback_row_end` (not `click_row_end`) for each labeled note row's `row_end` — a part label is a shortcut for "select everything under this label," lyrics included, so (unlike a note's own click target) it deliberately absorbs any following lyric verse row(s) — and accumulating the same running `global_measure_index` to give every part label in a system its `measure_index_start`/`measure_index_end` — that system's full measure range (including merged multi-measure rests, via `MeasureBlock::represents_measures`). Skips rows `expand::expand_note_part` never draws a `RowLabel` for (an empty `label`, or a lyric/absorbed-verse row) so a click target only ever exists where the label itself is visibly drawn.
- `grid_layout::click_targets::compute_all_lyric_click_targets` walks `for_each_system`, but per-syllable rather than per-note: `lyric_row_absolute_indices` mirrors `note_row_spans`'s cursor walk except it records each verse row's own single absolute row index instead of merging it into its note row's combined span, since a `LyricClickTarget` (unlike a `PlaybackCursorTarget`) never needs to span more than one row. One target is emitted per `(source_part_index, note_id, verse)` triple actually present in that row's elements — see **Lyric click target**.
- `grid_layout::click_targets::compute_all_lyric_label_click_targets` walks `for_each_system`, reusing the same `lyric_row_absolute_indices` walk as `compute_all_lyric_click_targets` (rather than `note_row_spans`) to find each verse row's own absolute row index, and the same running `global_measure_index` accumulation as `compute_all_part_label_click_targets` to give every verse label in a system its `measure_index_start`/`measure_index_end`. One target is emitted per verse row with a non-empty `label` (`layout::lyric_row_verse` reads the row's own `verse` field, the same peek `expand::expand_lyric_part` uses to build its `RowLabel` text) — see **Lyric label click target**.
- `grid_layout::click_targets::compute_all_bar_number_click_targets` walks `for_each_system`, alongside the same `global_measure_index` accumulation `compute_all_measure_click_targets` performs. `MeasureClickTarget`'s row range never reaches into the shared directive row above the musical rows (`for_each_system` advances `row_offset` past it before `visit` runs), so a measure's own bar number — drawn there by `layout_decoration::make_decoration_row` — falls outside every existing click target; this is a second, narrower target (`row`/`column`, not a row/column *range*) sized to just that bar number's own grid column, one row up (`row_offset.saturating_sub(1)`). Emitted for exactly the blocks whose bar number `make_decoration_row` actually draws — `layout_decoration::directive_line_should_emit(index, dec)` (shared by both) — so an otherwise-plain mid-system measure's undrawn bar number gets no click target either. See **Bar number click target**.
- `layout::note_part_sub_row_heights(base) -> [f32; 7]` returns `[tuplet_bracket, arc, above_dot, note_head, below_dot, half_ul, quarter_ul]` — the tuplet-bracket row is reserved unconditionally for every note-part row (like the arc row already was), so it counts toward every fixed sub-row index/count derived from it: `expand::expand_note_part`'s `arc_sub`/`head_sub` (`(1, 3)` for a note row vs. `(0, 1)` for a chord-only row, which has no tuplet-bracket row and keeps the old 4-row `chord_part_sub_row_heights` layout), `highlight::system_musical_row_count`, and `playback_cursor::note_row_spans` (both `7` in place of the old `6` for a non-chord row). Because this row is unconditional, every note-part row is one sub-row taller than before Step 7 added it, even for a score with no tuplets at all — unlike Step 6's grid-width/MIDI-tick changes, this is *not* a pixel-identical no-op for existing (non-tuplet) content.
- `grid_layout::click_targets::targets_on_page<T: Clone>(targets: &[(usize, T)], page_idx: usize) -> Vec<T>` is the generic filter behind every `GridPage`-per-page split in `layout()` — measure/playback-cursor/part-label/lyric/lyric-label click targets alike — replacing four near-identical hand-copied `*_on_page` functions.
- `config.hide_system_dividers` (from `Metadata::hide_system_dividers`, `# metadata` field `hide_system_dividers`, default `no`) gates `layout::build_page_rows`'s insertion of the full-width `GridContent::HorizontalLine` separator row between systems, and the corresponding gap in `layout()`'s page-break height accounting; when `true`, no divider row or gap is inserted between systems.
- `GridRow.has_label_region` (`true` for system rows built by `expand::expand_system_to_rows`/`layout_decoration::make_decoration_row`, `false` for header/footer/separator rows) marks which rows reserve `LABEL_COLS` columns for the part label. `GridRow::column_geometry(usable_width_pt, label_width_pt) -> ColumnGeometry` uses this flag to give the label region a fixed pixel width (`config.part_label_width_pt`) independent of that row's own `column_count`, while the remaining columns still split the rest of the width evenly — this is what keeps the part-label column the same rendered width across systems of differing musical density, rather than the old uniform `usable_width_pt / column_count` division which made the label's width vary with each system's content.
- `GridRow.measure_layout: Vec<MeasureColumnLayout>` (one entry per measure in the row's system, shared by every row of that system — built once by `layout::build_measure_column_layout(system, config)` and threaded into `expand::expand_system_to_rows`/`layout_decoration::make_decoration_row`) records each measure's `start_col`, `col_count` (`block_column_width`), `weight` (`layout_spacing::measure_note_weight`, the max summed real glyph width — measured via `font_metrics::advance_width_for_family`/`text_width_for_family` (family-aware since `notes`/`chords`/`note_dash` accept a `font_family` override — see **GlyphFontFamilies**) against `config`'s lyric font size, not a raw event count — of note/rest/percussion-hit/chord-symbol elements across the measure's part rows, so density scales with the busiest part rather than the part count; dashes and bar lines don't contribute here; a collapsed `MultiMeasureRest` gets `layout_spacing::multi_measure_rest_weight` instead — a real point width floored at `MULTI_MEASURE_REST_WIDTH` note glyphs, growing beyond that floor to match the count label's own rendered width once a run's count needs more digits than the floor allows), and `rod_pt`/`column_rods` — see **Rod and spring** in the glossary for what these are and how `column_geometry` splits width using them. Per-column weights within a measure (`layout_spacing::measure_column_weights`, also `config`-aware) are likewise real font-metric widths for glyph columns (notehead/rest/chord/dash/lyric), while `BarLine`/`Underline` columns keep their old arbitrary flat weights (`THIN_MARK_WEIGHT`/`0.0`) since they aren't glyphs with a measurable rendered width; a `MultiMeasureRest` column instead gets an even share of `multi_measure_rest_weight`'s real point total spread across the span. `layout_spacing::measure_column_sizes` computes `ColumnSizing { weight, rod_pt }` per column in one pass (max-across-parts, like the old weight-only version), and `measure_column_weights` is now a thin `#[cfg(test)]` wrapper over it that returns just the `weight`s. When `measure_layout` is empty (headers/footers/separators, or a row with no system), `column_geometry` falls back to the old single-scalar uniform division. Because `x_start`/`col_width` become piecewise-linear across segments, span-width consumers (`coordinate_resolver::resolve`'s arc/underline formulas, `coordinate_resolver::highlights`'s highlight/click-box formulas) must compute a span's width as `x_start(end) - x_start(start)` rather than `col_width(start) * span`, so a span crossing measures of different width still gets its true pixel extent. `ColumnGeometry::glyph_left_anchor_x(col, padding) -> f32` (`x_start(col) + padding`) is the shared helper for note/rest/dash/chord/percussion-hit/lyric-syllable anchoring and arc/underline/tuplet-bracket endpoints: every glyph anchors at the column's left edge plus `padding`, the same regardless of the column's own width or what else shares it — replacing an earlier weighted-centering formula that scaled a glyph's anchor toward the column's true center in proportion to its own weight share of the column's total, which made two visually similar notes land at different offsets depending on what else shared their column. `padding` itself is no longer one flat constant: every flush-left renderer (note head, rest, percussion hit, chord symbol, note dash, lyric syllable) now draws `TextAnchor::Start` at this anchor, so `coordinate_resolver::resolve::flush_left_padding` computes `padding = element_padding - bearing(leading_char)` per element, where `element_padding` is that content type's own configured horizontal padding (`RenderConfig::notes_horizontal_padding_pt`/`chords_horizontal_padding_pt`/`lyrics_horizontal_padding_pt`/`note_dash_horizontal_padding_pt`, sourced from `Metadata::*_horizontal_padding_pt` — see `ElementPaddings`) — the leading character's own left-side bearing (`font_metrics::glyph_left_bearing_for_family`/`cjk_glyph_left_bearing`, measured against the pinned font actually used to render that content type) — so every glyph's *ink*-left-edge, not just its anchor, lines up flush regardless of which content type shares the column (see `font_metrics::is_cjk_char`/`lyric_font_size`, the shared CJK-detection/font-size-selection helpers behind the lyric case). The tie/slur/underline/tuplet-bracket span markings in `resolve_span_marking` still use one flat `padding` (`notes_horizontal_padding_pt + note_number_width * 0.5`, approximating a note's *center* rather than any one glyph's bearing, since a span can cover notes of differing pitches/widths) — the same nominal `note_number_width` box the renderer's own `center` reconstructs in `glyph_renderers.rs::render_note_head` for its accidental/dot placement.

## Glossary

| Term | Definition |
|------|-----------|
| **System** | A horizontal row of measures that fit on one line of a page, packed purely by count: `grid_layout::layout_systems::pack_into_systems` groups measures into chunks of up to `config.max_measures_per_system`, never breaking early because measures have differently-shaped rows (differing parts, verse counts, `hide_resting_parts` suppression). Each system's rows are the union of every row across its own measures, in `[parts]` declaration order then verse order (`union_row_order`); a measure missing a row its system has gets it filled in by `pad_chunk_to_union`, in priority order: if some other row in that same block absorbed it (recorded in that row's `MeasureRow::absorbed_rows` — see Consolidator), the absorbed row's own original content is re-rendered here on its own — it's genuinely this part's real notes (real `note_id`s, real click/playback targets), just also drawn merged into another row elsewhere in the system, so the part isn't misreported as resting or silent; only when the `RowId` is genuinely absent from the block does it get synthesized as a full-measure rest or blank verse row, carrying no note identity (`make_padding_row` — see **Note identity**). Every resolved row's `label` is then (re)computed by `pad_chunk_to_union`'s `resolve_label`, which folds the row's own identity together with whichever of its `absorbed_rows` never get their own separate row anywhere in this system (i.e. aren't themselves a `RowId` in the union) — an absorbed row that *does* need its own row elsewhere only matched by coincidence in this one measure, so it's excluded from the fold rather than tainting the surviving row's label (this is what `consolidator`'s per-measure-only merge decision, above, can't itself know). The one exception that still forces an early system break is a `merge_duplicate_measures_across_parts` change between measures: that setting changes whether two parts merge into one shared row within a measure, so a mismatch means the row sets aren't just missing rows relative to each other, they're shaped incompatibly. |
| **Measure** | One bar of music. The score is a flat sequence of `MultiPartMeasure`s. |
| **Part** | A single instrument or voice track (e.g. soprano, bass). Declared in `[parts]`. |
| **Part Slice** | One part's notes and lyrics (one or more verses) for a single measure (`PartSlice`). |
| **Timed unit** | The compiler-stage trait (`TimedUnit`, `src/compiler/timed_unit.rs`) unifying `GroupedNote`, `GroupedChordNote`, and `GroupedPercussionHit` — anything that occupies a duration in the grid and exposes `duration`/`dotted`/`double_dotted`/`group_membership`/`group_continuation`/`slur_key`/`tie_to_next`/`tuplet`/`element_content()`. Used as shorthand in conversation/docs for "note, chord, or percussion hit" collectively, since all three compile through the same grid-column machinery. |
| **Ditto** | A measure where every input line was `"`, meaning it repeats the previous measure. Rendered as blank; audio output still uses the resolved content. |
| **Column** | A logical horizontal slot in the compiler's grid. Each beat occupies one or more columns. |
| **Rod and spring** | The spacing model `GridRow::column_geometry` (`src/grid_layout/column_geometry.rs`) uses to turn a system's measures/columns into pixel widths — named after the same rod-and-spring idea behind LilyPond's spacing engine (tracing back to Gourlay's spacing algorithm and Ross's *The Art of Music Engraving*). Every measure and every column within it first gets a hard-minimum **rod** — `MeasureColumnLayout.rod_pt`/`column_rods`, computed by `layout_spacing::build_measure_column_layout`/`measure_column_sizes` as real content width (`layout_spacing::column_rod`: a note-ish column's own `column_weight` plus a small, content-type-specific `layout_spacing::element_clearance_pt` clearance (the same configured `*_horizontal_padding_pt` value `flush_left_padding` anchors glyphs at — see above); a `BarLine` column's own small `BARLINE_MIN_WIDTH_PT`, since its `THIN_MARK_WEIGHT` is an arbitrary ratio rather than a measured width; `Underline` columns and the system's leading placeholder bar-line column get rod `0.0`, like their zero/excluded spring weight; a `MultiMeasureRest` row instead concentrates `layout_spacing::multi_measure_rest_weight`'s real point total as rod on its own start column, so the block's guaranteed minimum width grows with its count label instead of falling back to `MIN_MEASURE_WIDTH_PT` regardless of digit count) — floored at the measure level by `MIN_MEASURE_WIDTH_PT` for a degenerate near-empty measure and by the measure's own directive line's rendered width (`layout_decoration::directive_line_rod_width`, when `directive_line_should_emit` says that measure's line actually draws — bar number, section label, key/bpm/time-signature text — computed via the shared `font_metrics::directive_line_width`, which also backs the actual positioning math in `coordinate_resolver::content_conversion::directive_line_content`), so a measure whose directive text is wider than its own musical content still reserves enough rod that the text doesn't overflow into the next measure's directive line, with every column's rod then scaled up proportionally so `column_rods` still sums to exactly `rod_pt`. Because the next measure's own directive line is anchored at (and starts drawing from) this measure's *trailing bar-line column* rather than after it (see `layout_decoration::make_decoration_row`), the floor a directive line imposes isn't simply its own rendered width: since the proportional rescale also inflates that trailing bar line's own rod, `build_measure_column_layout` solves in closed form for the smaller pre-scale `rod_pt` that still leaves the directive's full width free of the bar line's post-scale share (`rod_pt >= directive_width_pt * content_rod / (content_rod - BARLINE_MIN_WIDTH_PT)`), so the next measure's directive line never starts drawing inside this one's reserved directive text. Only whatever width is left over after every rod in the row is satisfied (**slack**, clamped to `0.0` if rods alone already exceed the space available) gets distributed proportionally by the pre-existing **spring** weights (`weight`/`column_weights`) — so a column's width is always `rod + slack_share`, never less than its own rod. Unlike rod, a column's *weight* is not confined to an element's own start column: `measure_column_sizes` first scans every row for its `active_columns` (the raw grid ticks any row actually anchors an element to — an empirical scan, not a uniform GCD/divisor, so a coarser region next to a finer one never gets phantom mid-span columns), then for each element finds the next distinct active column its own row anchors something to (or `col_count` if it's the row's last) and splits that element's `column_weight` evenly across every active column in `[element.column, next_distinct_column)`, folding the max across rows per column as before. This lets a wide dash-free element (a chord symbol, say) that spans several ticks share its spring weight with whatever finer-grained content (an eighth note, a lyric syllable) another row anchors partway through that span, instead of piling all of it onto the element's own first tick — while its rod still occupies the full contiguous width a wide glyph needs before anything else can safely start. If a system's summed rods exceed the page's usable music width (`grid_layout::usable_music_width_pt`), slack clamps to zero and every measure/column renders at exactly its rod: the system deliberately overflows the page rather than silently compressing glyphs together, and `layout::layout` (`layout::system_overflow_diagnostic`) emits one `Diagnostic::Warning(WarningKind::MeasureOverflow)` per overflowing system, spanning the union of its measures' `MeasureBlock::source_span`s. |
| **Quarter-beat** | The smallest time unit used for duration arithmetic. A standard quarter note = 4 quarter-beats. |
| **Underline** | A horizontal line drawn below note heads to indicate duration subdivision. `level=0` = half-beat, `level=1` = quarter-beat. |
| **Octave Dot** | A dot drawn above or below a note head to shift its octave. Count = `octave.abs()`. |
| **Note Dash** | A visual `-` drawn after a note head for each extra beat of duration. |
| **Lyrics line** | One plain-text line per measure per `notes lyrics` part, tokenised into syllables and stored per measure (not as a global pool). Consecutive lyrics lines after the notes line are separate verses — see **Verse**. |
| **Verse** | One of a lyrics-bearing part's lyric lines for a measure, 0-indexed. The number of verses is per-measure (declared implicitly by how many consecutive `[Part]` lyric lines, or positionally-attached bare lines — see **Positional lyrics attribution** — follow the notes line) and can differ between measures for the same part; each verse is tie-paired against the notes independently and rendered as its own row. A verse-count change between two measures no longer forces a system break: a system's verse rows for a part are the union of every verse it has across the system's measures, and a measure missing a verse gets it padded in blank (see **System**). |
| **Positional lyrics attribution** | `desugar::attribute_data_lines` (`src/desugar/mod.rs`), scanning one measure group's raw data lines top-to-bottom: a real `[Key]`-prefixed line becomes `current_attribution_key`; a bare (unprefixed) line attaches to that key as a verse without itself becoming the new target (so consecutive bare lines become verses 1, 2, ... under the same key — the nearest preceding `[Key]` line wins when two parts precede it); a bare line with no attribution key yet is dropped (`RecoverableErrorKind::ScoreLineMissingKeyPrefix`). Each attributed bare line is synthesized into a `KeyedLine`/`SourceLine` carrying `is_positional: true` (mirroring `SourceLine::is_implicit_fill`'s pattern) so it rides the verse-counting machinery: `roles_for_group` gives `PartKind::Notes`/`PartKind::Chords` (any fixed-schema, notes-bearing kind except `Percussion`, which has no lyrics pairing to begin with) extra `Lyrics` roles, `verse_count = lines.len() - 1` with no floor (zero attached lines means zero verses). `is_positional` lines are excluded from `abbreviation_references` (no literal `[Abbrev]` token in source to feed rename-symbol) and from `key_map.rs`'s fixed-schema capacity check (so any number of positionally-attached verses never trip it, while two genuinely duplicated `[Abbrev]`-prefixed lines under a `notes`/`chords` part still do — a fixed-schema part has exactly one non-positional slot). Downstream, `grouper::attach_lyrics` (`part_grouper_group.rs`) tie-pairs a part's syllables against its own notes whenever it has `measure_syllables` at all — purely data-presence-based — and `interleaved_parser.rs` pushes one `lyrics_line_starts`/`lyrics_line_ends` placeholder per bar group per syllable-carrying track (updated in place, not re-pushed, by `process_lyrics_column_line`), so `attach_paired_lyrics`'s zip against `measures` stays 1:1 even for a group where a part's `Lyrics` role — and therefore its lyric line — is absent entirely. `midi::timing::note_timings_seconds(score: &Score, visible_tracks: Option<&[String]>, enabled_tracks: Option<&[String]>) -> Result<Vec<NoteTiming>, IrrecoverableError>` (and its range-scoped counterparts below) actually takes *two* independent track filters, since "which parts are physically rendered" and "which of those should sound in this one clip" are different concerns that must not be conflated:
- `visible_tracks` names which parts are actually rendered — the part-visibility toggle's own state, i.e. the same set `apply_track_filter` removes before the rendered SVG's own `compile()` call (see `src/filters.rs`, `render_svgs_from_source_filtered_with_lyrics`). Internally, `note_timings_seconds` clones `score` and runs it through the same `apply_track_filter` (`timing_note_timings::visible_score`) *before* computing `build_written_note_id_lookup`/`compile(score).blocks`, so `source_part_index` becomes the index within that visibility-filtered score's `measure.parts` — exactly the same compacted index the rendered SVG's `data-part-index` uses — and so a leading all-rest run that's only all-rest once a hidden sibling part's notes are removed collapses into the same single `MultiMeasureRest` block/`note_id` the render sees (`compiler::merge_rest_runs`). `None` keeps every part, matching an unfiltered render.
- `enabled_tracks` separately mutes playback down to a further, possibly narrower subset of those *visible* parts for this one call only (e.g. "play selection" narrowing playback to a few range-selected parts), without physically removing anything: it's applied to the *expanded* (navigation) timeline via `filter_expanded_tracks`, strictly after the visibility-filtered `note_id_lookup`/`written_blocks` are built, so it never influences block/note-id structure or `source_part_index` — a muted/repeated clip's `note_id`s still agree with the visibility-filtered `ColumnElement`s. `None` keeps every visible part.

Before this two-filter split existed, `note_timings_seconds` always built `note_id_lookup`/`written_blocks` from the fully unfiltered score, so `source_part_index` was always the note's true *written* index regardless of hidden parts — silently disagreeing with the rendered SVG's `data-part-index` whenever a part was hidden, and — worse — never recognising a rest run that only became all-rest once a hidden sibling's notes were removed, permanently desyncing the playback cursor across that span (it would get stuck on the merged rest's highlight and never advance). `worker/audioMessageHandlers.ts` now threads the worker's own `visibleTracks`/`enabledTracks` fields straight into WASM's `visible_tracks`/`enabled_tracks` parameters, so `source_part_index` returned to the frontend is already in the rendered SVG's compacted index space; `web/src/utils/noteTimingsPartIndex.ts`'s `remapNoteTimingsToVisiblePartIndex` (a client-side index remap that used to be the only fix for the index-compaction half of this problem) is consequently unused by `audioMessageHandlers.ts` now, though it's kept as a tested utility. The frontend (`components/playbackCursorPosition.ts`, `components/usePlaybackCursor.ts`) binary-searches each part's sorted `NoteTiming`s to find the active note at the current playback time and toggles the `fill` of that `(source_part_index, note_id)`'s `PlaybackCursorRect`(s) (see **Renderer**) — see **Playback cursor**. `midi::timing::note_timings_seconds_for_range(score: &Score, start_pos: usize, end_pos: usize, visible_tracks: Option<&[String]>, enabled_tracks: Option<&[String]>) -> Result<Vec<NoteTiming>, IrrecoverableError>` is the range-scoped counterpart backing `audio_source::note_timings_for_range_from_source`/WASM `list_note_timings_for_range`, used when playing a clip via `write_wav_for_measure_range_from_source` (e.g. "play from this measure") instead of the whole score: `start_s`/`end_s` are rebased to the *clip*'s own start (matching `measure_start_times_seconds_for_range`), but `note_id`s are still resolved via `build_written_note_id_lookup`/`compile(score).blocks` computed once over the passed-in `score` after `visible_tracks` filtering, which callers must pass as the *original, unexpanded* written score (unlike `measure_start_times_seconds_for_range`, whose `score` parameter is already the expanded score) — `note_timings_seconds_for_range` re-derives the expanded/playback-order timeline itself via `expand_navigation_with_note_positions` so `start_pos`/`end_pos` (already-resolved playback positions, not raw written indices — see **Navigation expansion**) line up with both the tick/tempo accounting and the visibility-filtered `note_id`s. `midi::timing::note_timings_seconds_for_literal_range` is the `respect_sequence: false` counterpart (see **Navigation expansion**), taking the same `visible_tracks`/`enabled_tracks` split. One exception to this identity scheme: a padded row synthesized by `grid_layout::layout_systems::pad_chunk_to_union`/`make_padding_row` (see **System**) for a measure genuinely missing a row its system has — a full-measure rest or blank verse — carries `ColumnElement::note_id: None` on every element, deliberately breaking the identity: it has no corresponding written note, no MIDI/WAV timing, and produces no `PlaybackCursorTarget`/`NoteClickTarget`/`LyricClickTarget`, rendering as an inert visual filler only. This does *not* apply to a row `pad_chunk_to_union` fills in from `MeasureRow::absorbed_rows` instead (see **System**) — that's the part's own original row, re-rendered with its own real `note_id`s intact, so it keeps its normal identity and real click/playback targets even though it's also drawn merged into another row elsewhere in the same system. |

| **Tuplet** | An `N:{notes}`/`N:M:{notes}` bracket in `.jianpu` syntax notating `N` notes in the time normally taken by `M` (implicit `M` from a standard-ratio table, or explicit via `:M`) — see `syntax.md`. Fixed by having `validate_and_pad_beats` itself compute `multiplier = crate::tuplet::resolution_multiplier_of(&events)` up front and run its truncation scan against a rescaled copy of `events` (`crate::tuplet::apply_resolution_multiplier(events.clone(), multiplier)`) compared against `expected * multiplier`, instead of the raw written totals — the truncation index still maps 1:1 onto the original (unrescaled) `events`, since rescaling never reorders or adds/removes events, so truncation and the deficit computation for auto-padding both stay correct in written-space. Reproduced (regression-tested in `interleaved_parser_padding_tests.rs`) with `3:{1_1_1_} 2 3 4` in a 4/4 bar: the eighth-note triplet's written total (`3*2=6`) plus three plain quarters (`3*4=12`) sums to `18` against a raw capacity of `16`, so the old check truncated the trailing "4" even though the triplet rescales to fill exactly one beat, making the true (rescaled) total exactly `16*multiplier`. **Verified failure mode (fixed)**: for a tuplet whose written total doesn't equal its rescaled/compressed total (any ratio where `num != den`, not just an expanding one) sharing a bar with any other content — or even alone, once the parser's nominal-capacity padding inserts a plain filler rest — `PartGrouper` used to rely solely on `push_timed_event`'s exact `current_beat == effective_capacity` check to close out a measure. Since a mismatched tuplet's rescaled total lands a beat or two off that boundary, the measure never closed there: its notes silently absorbed every subsequent `ParsedMeasureSlot::Real`'s events (each `begin_measure_slot` call just overwrote `resolution_multiplier` without flushing first) until some later event pushed `current_beat` over that slot's `effective_capacity`, at which point `flush_measure`'s `debug_assert!` (`src/grouper/part_grouper.rs`, ~line 106) tripped in a debug build, aborting the whole render; a release build (`debug_assert!` compiled out) would instead silently merge multiple source measures' notes into one produced `GroupedMeasure`, with no error surfaced. Reproduced with `2:{1 1} 2 3` in a 4/4 bar followed by any further measure (nominal sum 16 passes the pre-rescale check, but the duplet's notes expand by `den/num = 3/2` on top of the `resolution_multiplier = 2` scale-up, so the rescaled total is 40 against an effective capacity of 32) — and just as easily with a single tuplet type alone in a bar (e.g. `5:4:{1_1_1_1_1_}`), since the parser's auto-padding rest is sized off the same nominal total. **Fixed** by having `group_timed_track` (`src/grouper/part_grouper_group.rs`) call `PartGrouper::flush_measure` unconditionally once a `ParsedMeasureSlot::Real`'s events are all pushed, instead of relying on that exact-equality check to find the boundary — `validate_and_pad_beats` already guarantees one `Real` slot is exactly one source measure, so forcing the flush there is always correct regardless of any tuplet-rescale mismatch within it. `src/grouping.rs`'s `validate_measure_grouping` (half-bar-boundary crossing and dotted-eighth-tail rules, run from `interleaved_beat_padding::validate_and_pad_beats` at parse time) and `compiler::part_slice`'s underline/dash/beam-flush grid math (`PartSlice::resolution_multiplier` → `PartState::multiplier`, see **Compiler** above) both take/consume a `multiplier` parameter and scale their quarter-beat-grid constants by it. `validate_and_pad_beats` now passes its own computed `multiplier` (rather than always `1`) to `validate_measure_grouping`'s trailing call, alongside the unrescaled `events`; it's also exercised directly with a non-1 multiplier and artificially-rescaled events, in `src/grouping_tuplet_tests.rs`. MIDI tick export divides the multiplier back out: `midi::midi_notes::duration_to_ticks(quarter_beats: u32, multiplier: u32) -> u32` computes `quarter_beats * TPQ / (4 * multiplier)`, with `multiplier` threaded from `PartSlice::resolution_multiplier` through `midi::event_processing`'s `process_measure_notes`/`process_chord_events`/`process_percussion_events` and `midi::timing_note_events`'s `PartEventContext`/`TickSpanEvent`; `TPQ = 480`'s prime factors (2, 3, 5) don't cover every possible tuplet multiplier (e.g. a septuplet's `7`), so such a multiplier's ticks round down to the nearest tick rather than landing exactly — accepted rounding error, not addressed by raising `TPQ`. Grid-column pixel width needs no such division: `grid_layout::layout_spacing`'s `measure_note_weight` (cross-measure width) sums written `NoteHead`/`Rest`/`PercussionHit` *occurrences* (each `1.0`) plus each `ChordSymbol`'s own `chord_symbol_weight` (its rendered character count, so a slash chord's bass suffix like `2m/5` out-competes a bare `1` for width), and `measure_column_weights` (within-measure column split) normalizes by `column_weight_sum` — both counts are unaffected by `resolution_multiplier` (a tuplet's rescaled duration changes how many raw grid columns its notes span, not how many notes there are), so a rescaled measure's grid columns without any element already carry zero weight and contribute nothing to either split. Confirmed empirically: a single-measure triplet (`3:{1_1_1_} 2_ 3_ 4_ 5_ 6_`, multiplier 3) renders its 8 notes at uniform spacing, and all 14 `demo/*.jianpu` files render byte-identical SVG/MIDI output before and after this division was added (multiplier is always `1` there). A tuplet's notes also get a beam/underline reflecting their written duration (see **Compiler** above, `compile_unit`'s written-duration recovery), independent of the tuplet bracket drawn over them. |

| **Sequence resolution** | `resolve_sequence()` in `src/grouper/sequence_resolution.rs`, run inside `grouper::group()`. ## Web integration

The React app (`web/`) runs the compiler in a dedicated worker (`web/src/worker/jianpu.worker.ts`) backed by the `jianpu-wasm` crate. The main thread sends source text and asset bytes; the worker calls WASM exports and posts structured results back.

### Storage abstraction

- Module: `web/src/storage/`
- Key types: `StorageBackend` (`web/src/storage/types.ts`) — the interface both the browser-`localStorage` backend and a future GitHub backend implement; `FileStoreState` (`web/src/fileStore.ts`) remains the canonical in-memory shape used by every backend. `StorageBackend.load`/`createFile`/`duplicateFile`/`renameFile`/`deleteFile`/`restoreFile`/`saveContent` are async (to accommodate network-backed backends); `updateActiveContent` is sync with no persistence side effect. `saveContent` is the explicit call that persists the active file's content — debounce ownership lives in the hook layer, not the backend.
- `web/src/storage/localBackend.ts` — the only `StorageBackend` implementation so far. Thin async adapter over `fileStore.ts`'s pure, synchronous functions (`createFile`, `duplicateFile`, `renameFile`, `deleteFile`, `restoreFile`, `updateActiveContent`). Its `saveContent` is a no-op since `useLocalStorage` already persists on every state change.
- `web/src/storage/githubBackend.ts` — `GithubBackend` (extends `StorageBackend`), backed by GitHub's Contents API via `Octokit`. Config (`GithubBackendConfig`): `token`, `owner`, `repo` (always the fixed `jianpu-generator-storage`, see below), optional `branch`. Files always live under the fixed `scores/` top-level folder, with deleted files moved to a sibling top-level `trash/` folder, so further top-level siblings (e.g. `metadata`) can be added without a folder picker. No sha cache (refetches immediately before each write); rename/delete/restore are two sequential Contents API calls, not one atomic commit. Exposes a non-interface `lastError(): GithubBackendError | null` (`'conflict' | 'rate-limited' | 'network' | 'unknown'`) so the settings UI can render specific banners/prompts beyond the shared `SaveStatus`.
- `web/src/storage/githubAuth.ts` — OAuth device-flow auth, via `@octokit/auth-oauth-device` with a minimal duck-typed `request` stub that routes only the two CORS-blocked device-flow calls (`POST /login/device/code`, `POST /login/oauth/access_token`) through the Cloudflare proxy (see below); everything else (Contents API, `/user`, `/repos/...`) is called directly against `api.github.com`. `connectWithDeviceFlow(options)` runs the flow to completion and persists the token; `checkGithubAuthStatus()` validates a stored token against `GET /user`; `readStoredGithubAuth()`/`clearStoredGithubAuth()` are imperative accessors (for non-component callers) and `useGithubAuthToken()` is the reactive hook equivalent (for the settings UI). Disconnecting only clears the local token — it does not revoke it on GitHub's side.
- Entry: `useStorageBackend()` in `web/src/hooks/useStorageBackend.ts` — holds the `FileStoreState` in React state and exposes `store`/`setStore`/`backend`/`saveStatus`/`preference`/`switchBackend()`/`forceSave()`/`flushPendingSave()`. `local`'s state lives in `useLocalStorage` (seeded synchronously through `localBackend`'s local-only read helpers); `github`'s state is fetched via `backend.load()` into a plain `useState` whenever the backend identity (kind/owner/token) changes. Callers `await backend.xxxFile(store)` for structural operations (create/duplicate/rename/delete/restore — hit the backend immediately), then `setStore` the result; content edits go through the existing `setStore`/`backend.updateActiveContent` path and are separately debounced (`AUTOSAVE_DEBOUNCE_MS`, ~20s, via `use-debounce`'s `useDebouncedCallback`) into a `backend.saveContent()` call — one shared cadence for both backends, immaterial for `local` (no-op `saveContent`), kept low-frequency for `github`. `switchBackend(target)` persists the choice under `jianpu:storage-backend:v1` (`{ backend, github?: { owner } }`), force-flushing (and awaiting) any pending GitHub save first, and always lands on the demo file — there is no per-backend "last active file" memory. `flushPendingSave()` similarly force-flushes a pending GitHub save without cancelling the debounce timer or switching backend; `App.tsx`'s `handleSelect` calls it before changing the active file tab, since `shouldScheduleAutosave` deliberately does not schedule a new save on such switches.
- `web/src/components/StorageSettingsModal.tsx` — the settings UI that makes the GitHub backend reachable: a Radix Dialog offering "This browser" vs. "GitHub repository", an inline device-flow connect step (rendering `githubAuth.ts`'s `onVerification` `user_code`/`verification_uri`) when GitHub is selected but not connected, and, once connected, `@username` / repo-in-use (`<repo>/scores`) / "Disconnect". Repo selection is fully automatic: `ensureStorageRepo(octokit, owner)` (exported from this file) calls `octokit.rest.repos.get()` for the fixed `jianpu-generator-storage` repo name and creates it (private) on `404` — no picker, no confirmation prompt. Also renders `githubBackend.ts`'s `lastError()` as a rate-limit/offline banner, and resolves `409` conflicts via `resolveGithubConflict()` (also exported), a minimal "overwrite mine" (retry `saveContent`) vs. "discard mine" (`backend.load()` then `updateActiveContent` with the remote content) choice — no 3-way merge. `FileList.tsx`'s `FileTabBar` exposes the entry point (a "Storage…" button plus a saving/saved/offline status badge, `onOpenStorageSettings`/`saveStatus` props); `App.tsx` owns the modal's open state and threads `backend`/`preference`/`switchBackend`/`saveStatus` from `useStorageBackend()` down to both.
- **`cf-oauth-proxy/`** — a separate Cloudflare Pages Functions project, **not** part of `web/`'s build (Vite/pnpm never sees it; it's deployed as its own Cloudflare Pages project per `cf-oauth-proxy/README.md`). It exists solely to relay the two GitHub OAuth device-flow calls that don't send CORS headers (`POST /login/device/code` → `/device/code`, `POST /login/oauth/access_token` → `/oauth/token`), injecting the OAuth App's client secret server-side; every other GitHub API call the app makes goes straight from the browser to `api.github.com`. `web/`'s build points at a deployed instance of it via the `VITE_GITHUB_OAUTH_PROXY_URL` env var (set in `.github/workflows/pages.yml`); there is no revoke/disconnect endpoint in v1.

### Source editing

- Module: `src/source_edit/`
- Entries: `source_edit::update_part_declaration(source, abbreviation, new_mode, new_soundfont, new_volume, new_octave_offset) -> Option<String>`; `source_edit::shift_part_octave(source, abbreviation, delta: i8) -> String`; `source_edit::shift_range_octave(source, ranges: &[ByteRange], delta: i8) -> ShiftRangeOctaveResult`
- `update_part_declaration` rewrites a single `# parts` declaration line in place (mode, optional quoted soundfont, optional volume `%`, optional octave offset). Used by the Edit Parts modal instead of any TypeScript parser.
- `shift_part_octave` bulk-rewrites the `'`/`,` octave marker on every `ScoreEvent::Note` belonging to one part in `# score` (the "notation octave" control in the web editor — distinct from `update_part_declaration`'s MIDI-only `octave_offset`, which never touches rendered notation). Parses via `parser::parse` to read each note's resolved `octave: i8` and full-token `Span` (`ParsedTimedTrack::measure_slots`), then splices new marker text into the raw source back-to-front by span. Infallible / best-effort, mirroring `update_part_declaration`'s "not found → unchanged" convention: an unknown abbreviation, a `follow[X]` part (no notes of its own), `delta == 0`, or a parse failure all return `source` unchanged. No clamping on the resulting octave.
- `shift_range_octave` is `shift_part_octave`'s counterpart for the editor toolbar's "Octave up"/"Octave down" buttons: instead of one named part, it shifts every note across every part whose `Span` overlaps any of the (generally disjoint — e.g. a clicked part label's multicursor selection) `ranges` — the web editor's current text selection, so a selection crossing a measure or part boundary shifts notes in every measure/part it touches. Shares `shift_part_octave`'s edit-collection/splicing helpers, `follow[X]`-safe (no events to match), and unchanged-on-`delta == 0`/parse-failure conventions. Unlike `shift_part_octave`, it returns a `ShiftRangeOctaveResult { source: String, ranges: Vec<ByteRange> }`: `ranges` is the caller's own input `ranges`, remapped forward through the edits to their new `[start, end)` byte spans *in the new source* (`remap_ranges`/`remap_offset`, biasing a range's start to an overlapping edit's new start and its end to that edit's new end), preserving the input ranges' count and shape — a contiguous multi-note range selection stays one contiguous range, a disjoint multicursor selection stays that many disjoint ranges — rather than exploding into one range per shifted note. This lets the editor restore its selection in the same synchronous call that applies the new source (`web/src/types.ts`'s `EditorHandle.replaceContentWithSelections`) — see `HANDOFF-octave-toolbar-part-label-selection-bug.md`.

### Split-track export

- Module: `src/split_track.rs`
- Entries: `write_split_pdfs_from_source(source, filename, base_name, tracks_filter, fonts) -> Result<Vec<SplitPdfEntry>, IrrecoverableError>` (`pdf` feature); `write_split_midis_from_source(source, filename, base_name, tracks_filter) -> Result<Vec<SplitFileEntry>, IrrecoverableError>` (`midi` feature); `write_split_wavs_from_source(source, filename, base_name, tracks_filter, sf2_bytes) -> Result<Vec<SplitFileEntry>, IrrecoverableError>` (`wav` feature); `write_split_mp3s_from_source(source, filename, base_name, tracks_filter, sf2_bytes) -> Result<Vec<SplitFileEntry>, IrrecoverableError>` (`mp3` feature)
- Each parses/compiles the source once, then renders/synthesizes one output per track (`tracks_filter` empty → all score tracks).
- Key types: `SplitPdfEntry` (`track_name`, `filename`, `pdf`), `SplitFileEntry` (`track_name`, `filename`, `bytes` — shared by the MIDI, WAV, and MP3 variants)
- `zip_split_pdfs(entries: &[SplitPdfEntry])` / `zip_split_entries(entries: &[SplitFileEntry])` archive the entries into a single ZIP (`Vec<u8>`), one file per track named via `split_track_filename`.
- `src/lib.rs`'s `write_midi_from_source_filtered(source, filename, enabled_tracks, instruments) -> Result<Vec<u8>, IrrecoverableError>` (`midi` feature) is the whole-score counterpart used by `generate_midi`, mirroring `write_pdf_from_source_filtered` and `write_wav_for_measure_range_from_source`.

- Entry: `list_part_declarations_from_source(source, filename, instruments) -> Result<Vec<SourcePartDeclaration>, IrrecoverableError>`

### Rename-symbol support (source-level)

- Module: `src/symbols.rs` (re-exported from `src/lib.rs`)
- Entries: `collect_symbols(document: &ParsedDocument) -> Vec<Symbol>`; `rename_edits(document: &ParsedDocument, kind: SymbolKind, old_name: &str, new_name: &str) -> Vec<TextEdit>`
- Key types: `SymbolKind` (`Abbreviation` — parts and groups share one namespace, so both kinds of declaration collect under it — or `SectionLabel`), `Symbol { name, kind, occurrences: Vec<SymbolOccurrence> }`, `SymbolOccurrence { span, role: OccurrenceRole }` (`Declaration` or `Reference`), `TextEdit { span, replacement }`
- Built entirely on spans `ParsedDocument` already tracks (see **Rename-symbol support** in the glossary for which fields) rather than a separate parse pass; `rename_edits` is `collect_symbols` plus a lookup and a flat map from occurrence to replacement text, so it never mutates source itself — callers apply the edits.

### Score formatting (source-level)

- Module: `src/format_source.rs` (re-exported from `src/lib.rs`)
- Entry: `format_score(source: &str) -> String`
- A normal-editor toolbar action: per `# score` measure group, drops `[Key]` data lines that are entirely redundant with implicit-fill (an all-rest line for a `Notes`/`Chord`-role occurrence, an all-`_` line for a `Lyrics`-role occurrence), sorts the surviving `[Key]` lines into `# parts` declaration order, and collapses whitespace to single spaces on every surviving directive/data line. A key's droppable lines must be a *trailing* run (dropping an earlier verse out from under a later one with real content would shift it into the wrong slot) and dropping is blocked outright if it would leave the group with zero data lines (a parse error). `follow[X]` parts are excluded from redundant-line dropping (an explicit rest there is real content, not filler) but still take part in sorting.
- Sorting groups a key's surviving lines into one block that moves together, regardless of how interleaved with other keys' lines it was in the source; a bare (positional) lyrics line (see **Positional lyrics attribution** in the glossary) joins whichever `[Key]` line's block most recently preceded it, so it travels with its part instead of being treated as unattached content. A block for an unrecognised key, or a standalone positional-lyrics caption with no preceding `[Key]` line in the group, keeps its original relative position, ordered after every recognised part's block.
- Classification/removability is hand-rolled directly from each key's raw per-group line count (mirrors `desugar::roles_for_group`'s static-kind branch without invoking it), and the output is spliced together directly from the filtered/reordered/normalized raw lines. `desugar::desugar_groups` is still run once over the filtered groups as a best-effort validity check (falling back to `source` unchanged on `Err`), but its materialized output is discarded. Real implicit-fill for the dropped lines happens later, ordinarily, whenever the resulting `.jianpu` source is actually parsed — exactly as it already does for any measure group that omits a part's line.
- Infallible / best-effort, mirroring `source_edit::update_part_declaration`'s "not found → unchanged" convention: a missing/empty `# parts` or `# score` section, or an internal parse failure, returns `source` unchanged.

### WASM boundary mechanism (`crates/jianpu-wasm`)

The Rust↔TS boundary is `wit-bindgen`/`cargo-component`/`jco` — not
`wasm-bindgen`/`tsify` (fully replaced; see
`PLAN-wit-bindgen-migration.md` for the migration's rationale and
history). One `.wit` schema (`crates/jianpu-wasm/wit/world.wit`, flat
world-level `record`/`variant`/`enum`/`export` declarations, kebab-case
names) is the single source of truth for every exported function's
*full* signature — inputs and outputs alike — generated into real Rust
types via `wit_bindgen::generate!` and real TS types via `jco
transpile`, so a shape mismatch on either side is a compile error, not
a runtime `JsValue`/`any` surprise.

- `crates/jianpu-wasm/src/component.rs` — the crate's one and only
  `Guest` impl (`struct Component`), implementing every exported
  function against the same internal `crate::responses::*`/
  `crate::part_declarations::*`/`crate::symbols::*`/
  `crate::selection_range::*` functions the rest of the crate (and its
  own unit tests) call directly. Converts WIT-generated
  records/variants to/from this crate's own internal `*Out`/`*In` types
  at each function's boundary (e.g. `part_to_wit`, `render_response`'s
  `documents`/`diagnostics` conversion) — the only place in the crate
  that names both type families.
- Build: `cargo component build --features wav,mp3,pdf,midi --target
  wasm32-unknown-unknown` (workspace's `release-wasm` Cargo profile for
  the real asset build — `debug = false, strip = true`, keeping the
  native `jianpu` CLI's own `[profile.release]` untouched) produces a
  component `.wasm`; `jco transpile <that>.wasm --instantiation async
  -o crates/jianpu-wasm/pkg-component` generates the JS glue
  (`jianpu_wasm.js`/`jianpu_wasm.d.ts`/`jianpu_wasm.core.wasm`,
  gitignored, like the crate's own `target/`). `web/package.json`'s
  `build:wasm-component` script runs both steps in sequence and is
  wired into `predev`/`prebuild`/`build` — the only wasm build path;
  there is no wasm-bindgen/wasm-pack fallback left anywhere in the repo.
- `web/src/wasmInit.ts`'s `ensureWasmModule`/`ensureWasmInit` fetch and
  compile the component's core `.wasm` once (shared in-flight promise
  across every caller, including a `postMessage` hand-off of the
  compiled `WebAssembly.Module` to the render worker) and instantiate
  it via the jco-generated `instantiate((_) => module, {})` (no host
  imports needed on `wasm32-unknown-unknown`). `web/src/worker/jianpu.worker.ts`
  does the same on its own thread once it receives the module.
- `web/src/jianpuWasm.ts` is a compatibility bridge, not a
  transliteration: it exposes the exact function names/signatures/
  output shapes every other file in `web/` already expects (snake_case
  fields where the pre-migration `tsify` output used snake_case, a flat
  `{ status: "ok" | "err", ... }` response envelope, `SvgDocumentOut`'s
  recursive element tree, etc. — the shapes this "WASM exports" section
  and the rest of this document describe), converting to/from the raw
  WIT-generated `Root` object internally (`setWasmRoot`, called once by
  `wasmInit.ts`/`jianpu.worker.ts` after instantiation). Every input
  argument passed to `Root` is genuinely WIT-typed end to end — the
  actual type-safety gain over the old `JsValue`/`serde_wasm_bindgen`
  boundary — while outputs keep their pre-migration shape/naming
  convention rather than propagating a field-renaming sweep across
  `web/`'s ~50 consuming files, since outputs were already fully
  generated and type-safe under `tsify` before this migration and the
  naming convention itself was never the problem. Every function
  documented below is this bridge's real, present export; nothing in
  this section changed as a result of the boundary-mechanism swap.
